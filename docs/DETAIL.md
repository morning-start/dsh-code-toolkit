# 代码工具箱

三条检查默认在**当前会话**里执行：命令解析完范围，把任务作为一条消息投进会话，你能看见它读哪些文件、跑哪条门禁。加 `sub` 才换成**独立上下文的原生 spawn agent**——子 agent 不看当前对话历史，自己去读 Git、源码、调用方和测试，报告随后作为一条消息回来。另有 `/code-caption` 与 `/pua`，它们不 spawn，而是把文本注入当前会话。

## 命令

| 命令 | 作用 | 是否改文件 |
| --- | --- | --- |
| `/code-review` | 审查改动，出带优先级的报告 | 只读 |
| `/code-simplify` | 简化代码：功能逐位不变 | 默认直接改；加 `report` 只出计划 |
| `/code-scrub` | 清理隐私信息：密钥、密码、账号、本机路径 | 默认直接改；加 `report` 只出报告 |
| `/code-caption` | 把难任务装进 caption 循环：一步一验，过程落成台账 | 由循环里的每一步决定 |
| `/code-status` | 查看运行状态或最近一次结果 | — |
| `/code-cancel` | 取消正在运行的任务 | — |

三条检查命令默认在当前会话执行，加 `sub` 交给隔离子 agent：`/code-review sub`、`/code-simplify sub --base main`。

## 默认行为

每条命令在输入为空时都有一套默认值，不需要你回答任何问题：

| 命令 | 空输入时的默认 |
| --- | --- |
| `/code-review` | 工作区有未提交改动时**只看未提交的**；都提交了就**看当前分支相对基线的改动**；分支没有独立基线时看**最近 5 个提交**；只读 |
| `/code-simplify` | 整个项目、当前分支、**直接改** |
| `/code-scrub` | 整个项目、**直接改** |
| `/code-caption` | 继续当前会话正在进行的任务 || `/pua` | 阿里风味 |
| `/code-status`、`/code-cancel` | 不需要输入 |

通用规则：执行者是当前会话（加 `sub` 才用隔离子 agent），模式是写（加 `report` 只出报告）。

范围会先做一次**空范围预检**：工作区干净、分支又没有基线时，命令直接返回「没有可审查的改动」并提示用 `--base` / `--commit` / `--files`，不会白跑一轮。

回执会写明这次落在哪个范围（`working tree vs HEAD` / `HEAD vs main` / `last 5 commits` / `whole project`），因为默认范围是从仓库状态推出来的，不写出来你就不知道它到底在看哪部分。

会话内执行时，报告是写给人看的 Markdown；`sub` 时子 agent 返回 JSON，由外壳解析后渲染。

## 收窄范围

默认范围见上表；要收窄就一行写清：

```text
/code-review --base main
/code-review sub --commit 1a2b3c4
/code-simplify --files src/app.js,src/util.js
/code-simplify report
/code-simplify sub report --base main
/code-simplify 只看 src/ 下新增的错误处理，别动测试
```

`--files` / `--base` / `--commit` 指定范围，其余文本按自定义说明处理。`sub` 交给隔离子 agent，`report` 只出报告——两者都是词，位置随意，可叠加。**默认直接改**：`/code-simplify` 与 `/code-scrub` 不再弹窗问「只出报告还是直接改写」，要报告就加 `report`。

### 为什么命令必须声明 input

声明了 `input`，从 `/` 菜单里选中命令只会**插入令牌**，后面可以继续补参数；不声明 `input` 的命令是「选中即执行」，Tab 也等同于回车，没法先插入再输入。所以三条命令都保留 `input`。

回车之后的处理方式是关键：handler **立刻返回**一句回执，输入框当场清空；选范围、跑子 agent、渲染报告都在后台继续，结束时用 `agent.followup` 把报告作为一条用户消息发回会话，消息里要求模型原样转述、不要重跑。这样既不会冻结输入框，也不会丢掉结果。

这个结构来自社区插件 `dsh-code-review` 与 `dsh-simplify`：命令只当回执，真正的产物走会话消息。区别在于我们的三条命令仍然交给**独立上下文的子 agent**，而不是当前会话的 Agent——审查和清理要的是不受当前对话影响的第二双眼睛。

失败也要发消息：范围选不出来、子 agent 报错、被取消之前就失败，都会以一条「未完成」消息说明原因，否则用户只看到输入框清了、什么也没有。

## 一个外壳

七条命令共用同一个类 `SessionCommand`（`src/command.js`）。每条命令在 `index.js` 里只是一份声明：`kind`（`task` / `inject` / `local`）、是否只读、是否问「直接改写」、报告是否结构化、用哪个 persona、菜单文案的 i18n key。

类负责的是所有命令共同的部分：

- 立刻返回回执，任务在后台继续；
- 范围选择（`userQuestions`）；
- `sub` 分流：默认投递给当前会话，`sub` 才起隔离子 agent；
- 失败时发一条说明，不静默；
- journal 的 `submitted` / `running` / `finished` 三种状态。

新增一条命令时只写声明，不要绕开这个类直接注册——测试会检查 `index.js` 里没有 `ctx.commands.register`。

## 提示词的组织

persona 不是一个文件，而是 `agents/<role>/` 下的一棵树：

```text
AGENT.md               常驻：注入子 agent 的 system prompt
references/*.md        按需：子 agent 用读文件工具自己取
examples/*.md          按需：示范"什么算够好"
```

`AGENT.md` 末尾有一张表，写明"什么时候读哪一份"。任务里会给出 `Reference directory` 的绝对路径，子 agent 自己决定读不读、读哪份。读不到也不影响：核心指令是自足的。

这样做的好处和 skill 的 progressive disclosure 一样：常驻上下文短，深度内容不占预算；但触发是命令、运行是独立 agent，不依赖模型检索。

## 审查：八道门

一个候选问题要同时满足八条才算发现，否则丢掉——误报的代价是作者不再读报告：

1. 影响正确性 / 性能 / 安全 / 可维护性
2. 离散且可行动，不是"这块很乱"
3. 修复不要求项目本身没有的严谨度
4. **是本次改动引入的**，不是既有缺陷
5. 作者知道后会去修
6. 不依赖对作者意图的臆测
7. 若影响别处，能指出是哪一处
8. 明显不是有意为之

来源是 OpenAI Codex 的审查标准（`review_request.rs` @ `a592c38c`，Apache-2.0），在 `references/rubric.md` 里保留了原文要点与出处。

| 级别 | 含义 |
| --- | --- |
| **P0** | 正确性 / 数据丢失 / 安全 / 契约破坏，合并前必须修 |
| **P1** | 真实路径上的可能 bug、资源泄漏、竞态、缺失错误处理 |
| **P2** | 有具体代价的可维护性问题 |
| **P3** | 项目有明确约定时的风格问题 |

## 审查的输出

子 agent 被要求返回**一个 JSON 对象**（Codex 的 `findings` / `overall_correctness` / `overall_explanation` 结构）。插件解析后渲染成 Markdown：优先级标签 + `[路径:起–止](路径#L起-L止)` 的本地文件链接。

模型不总听话，所以解析器同时接受：裸 JSON、围栏里的 JSON、JSON 前后带说明、`priority` 写成 `"P2"`、`line_range` 写成 `"12-14"`、字段别名（`file` / `path` / `line`）。完全解析不出来时按纯文本原样透传——报告难看一点，好过丢掉。

## 简化的三条铁律

1. **功能逐位不变**——输入、输出、异常类型与消息、日志内容、副作用与顺序、边界与顺序行为，全不变。
2. **以项目既有规范为准**——先读 `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING` 与周边代码，不自创风格。
3. **清晰优先于简短**——压缩到看不懂不算简化。

六类操作：去冗余、降嵌套、提可读、清注释、改日志、去自证测试。反模式（顺手改功能、范围蔓延、过度简化、简化出抽象、删必要上下文、嵌套三元）写进 persona，由子 agent 自查。

**计划按价值排，不按条数算。** 结构重复 > 死重量 > 热路径可读性 > 机械整理；机械项按文件合并成一条，计划里全是未使用 import 时要自己说出来，并交代前三级查到了什么。覆盖也要说准：`Files read in full` 只算真正打开读过的文件，只 grep 过或只跑过 AST 的进 `searched only`。

**没门禁就不改写。** 仓库有测试就先跑测试；没有测试就先建一条基线——编译/导入冒烟、拿真实输入跑真实入口并对产物取哈希、给纯函数钉一张输入输出表——然后一次只改一批、每批之后重跑同一条基线。连基线都建不起来就不改写，交回计划并说清缺什么。

**未处理要分类**：`defect`（真缺陷，单独修）、`behaviour-risk`（看着能合，但空值语义或 tie-break 不同）、`too-big`（结构重构，另开任务）、`intentional`（代码里写明的有意重复）。平铺一张清单等于把判断留给用户。

"功能不变"是要论证的，不是要声称的：`references/behavior-preservation.md` 列了 15 项会静默变化的东西（异常类型、副作用顺序、`??` 与 `||`、迭代顺序、浮点、时区、懒求值、mutation…），apply 前逐项过。改文件时锚点要先确认唯一、改完读回；写入失败（权限、占用）算发现，不算可以重试的循环。

## 隐私清理

`/code-scrub` 找一个仓库里不该提交的东西：密钥、令牌、私钥、带密码的连接串、内部邮箱与主机名、账号 id、本机路径（`C:\Users\<名字>\`、`/home/<名字>/`、UNC、机器名）。

### 两条铁律

1. **绝不复述密钥。** 报告里只出现脱敏形态：`sk-ab…9f`（前 4 后 2）、`<12 chars>`（只给长度）、`-----BEGIN … PRIVATE KEY-----`（只给头）、`C:\Users\<user>\…`（保留形状去掉身份）。一份把密钥抄进报告的报告，只是把泄漏搬到了会话记录、日志和用户接下来贴出去的 issue 里。
2. **默认改，报告另说。** 加 `report` 只出报告；要改就必须验证，不过就回退。

### 分类与优先级

| 级别 | 含义 | 例 |
| --- | --- | --- |
| **P0** | 活的凭据：读到就能以项目或某人身份认证 | API key、私钥、带密码的数据库 URL、webhook 路径里的令牌、提交进仓库的 `.env` |
| **P1** | 能把真实的人或系统对应起来的账号信息 | 内部邮箱、内部主机名、RFC1918 地址、账号 / 租户 id |
| **P2** | 本机环境细节 | `C:\Users\<名字>\`、机器名、OS 用户名、IDE 里的绝对路径 |
| **P3** | 弱信号：像密钥但可能是占位符或公开值 | 文档里的测试 key |

判断不了是不是活的，就在正文里说明，并把级别**降一档**——一个错误的 P0 比漏掉一个 P3 更快让人不再相信报告。

### 不算发现

- **引用而不是值**：`process.env.API_KEY`、`os.environ[...]`、`os.Getenv(...)`、`vault:` / `secretsmanager:` 引用
- **占位符**：`<your-key>`、`YOUR_TOKEN_HERE`、`changeme`、`xxx`、`***`、`sk-test`、空字符串
- **公开元数据**：`package.json` 的 `author`、`LICENSE` 的版权行、README 里的公开联系方式、仓库地址、npm scope
- **长得像但不是**：commit SHA、文件哈希、UUID、构建号、base64 图片、公共 DNS 地址
- **测试夹具**：`test-key`、`test@example.com`、mock 值

这条清单是成败关键：一个把 `process.env.API_KEY` 和作者邮箱都报出来的工具，跑两次就没人看了。

### 改写怎么改

按文件类型替换，保留结构、保持文件可解析：`.env` 置空或写占位符；JSON 写 `""`；YAML 用 `${API_KEY}`（当消费方会插值时）；源码改成该语言惯用的环境读取（JS `process.env.X`、Python `os.environ[...]`、Go `os.Getenv`）；文档写 `<redacted>`；本机路径改成 `~` 或 `os.homedir()`。

验证三件事：字面量确实没了（用脱敏片段去 grep，不要用完整值）、文件仍能解析、`git diff --stat` 只动了该动的文件。

### 改写不了的东西

改写只清理工作区。凭据仍在 `git log`、每个克隆、每份备份里——**必须在服务商那边轮换**。报告每次都会写明这一点。

## caption 循环

`/code-caption <任务>` 注入的是一套**循环**，不是一张清单。清单假设世界按写下的顺序展开；循环假设每次动手都会带回新信息，下一步由这条信息决定。

一轮的形状：

1. 先读台账（压缩之后，台账是唯一还记得细节的东西）
2. 看真实状态（跑那条能证明当前说法的命令，或读要改的文件）
3. 只选一步（一步只改一件事，否则红了不知道是谁红的）
4. 动手（锚点唯一、改完读回）
5. 跑门禁（退出码决定，不是判断决定）
6. 新守卫要做反证（弄坏它 → 必须红 → 复原 → 必须绿）
7. 记一条 caption 并提交
8. 重排下一步（如果这一步改变了任务形状，说出来）

产物是目标仓库里的 `docs/caption/<slug>.md`：头部是任务、验收判据、门禁命令；每条记 `Saw / Decided / Did / Evidence / Outcome`，`Outcome` 只能是 `done`、`dead end`、`unverified`。

- **台账位置可配**：`ledgerDirectory`，相对路径按项目根解析；回执里会写出真实路径。
- **重复执行不重复注入**：同一会话里第二次 `/code-caption` 只补任务和台账位置，不再塞一遍 5 KB 协议——协议已经在对话里，两份只会互相打架。
- **分派只有两条路**：`subagent`（新上下文，brief 里写清路径与门禁）和插件自己的 `sub`（`/code-review sub` 等）。同一片工作只用其中一条；`sub` 是单飞的，同一会话里同时只能跑一个，`subagent` 不受这个限制，靠写集纪律约束。
- **专家写在 brief 里**：需要专才时，把「身份与标准、看什么、什么算发现、什么不算、输出形状」五段写进派工单，而不是只说「你是资深工程师」。方法见 `agents/caption/references/experts.md`，里面有一弱一强两个对照。
- **两条常用流程**：改代码（需求 → 调查 → 方案 → **人类审核** → 执行 → 测试 → 人类确认 → 改文档）和改文档（需求 → 调查 → 方案 → **人类审核** → 执行 → 总结）。审核是硬门禁，没批不许动手；流程写在台账头部。见 `agents/caption/references/flows.md`。

三条规则撑起全部价值：**没有证据不许声称**（"测试通过"是一条命令和它的输出，不是一句话）、**死路要留痕**（否则下一轮再踩一次）、**判据满足才收口**（清单空了不算完）。收尾必须列出未验证项——没验的东西写出来是诚实，藏起来就是让用户替它担保。

### 分派

协议允许把工作交给子 agent，但只在切片**不会相撞**时，并且分成两条线路：

| 线路 | 能不能并行 | 约束 |
| --- | --- | --- |
| 分析（只读） | 可以 | 不写文件、不 `git add`、不格式化；一个问题一个 agent；结果是输入不是裁决 |
| 实现（写入） | 仅在路径互不相交时 | 每个 agent 独占一组路径；共享文件（barrel / index / 配置 / lockfile / 共用测试）只归一个主人 |

派活的 brief 必须写：线路、可读路径、可写路径、绝不能碰的东西、要跑的门禁、结果的形状、以及"需要范围外文件时停下报告"。合并后由主会话跑**整条**门禁——每个 agent 自己的绿灯不代表合并后的树是绿的；两处局部正确的改动仍然可能在接缝处打架。

不该并行的：整个仓库级别的改动（重命名、依赖升级）、所有切片都依赖的同一个测试文件、有顺序要求的迁移。把没切开的活分派出去，得到的不是速度，是冲突。

`/code-caption` 与 DSH 自带的 `/plan` 是串联关系：`/plan` 负责探索与方案批准，`/code-caption` 负责批准之后的执行与证明。

## PUA 协议

`/pua [风味]` 不 spawn、也不改文件，只把一份协议作为一条消息注入当前会话：

- **三条红线**：闭环（说完成要给出命令和输出）、事实驱动（环境/权限/用户归因先验证）、穷尽（五步没走完不许说做不到）。
- **压力升级 L0–L4**：同类失败 2 次换方法，3 次读源码写三个假设，4 次走 7 点清单，5 次以上停下仪表化、二分定位。
- **五步**：逐字读错误 → 复现并缩小 → 三个假设各配一个检查 → 换方法 → 贴出命令和输出。
- **冰山法则**：一个问题进，一类问题出；修 A 不查 B，等于写两份复盘。

风味只决定语气：`/pua` 默认阿里，`/pua huawei` / `musk` / `jobs` 等换风味，`/pua list` 列出全部。协议里明确禁止为了让门禁变绿而删断言、跳过检查，或去读隐藏答案；风味不能成为抄近路的理由。

## 默认在会话里，`sub` 才隔离

三条检查默认在当前会话执行：你能看见它读什么、改什么，发现问题可以立刻打断；范围、门禁、结论都在同一条时间线上，不用在两段对话之间对照。

加 `sub` 才交给独立 agent：主 agent 审查自己的改动会受上下文影响——它“知道”自己为什么这么写。独立 agent 只看到代码和 Git 历史，更接近下一个接手的人，也不会把整段对话背进去。代价是过程不可见，只能等报告回来。

## 状态与落盘

每次运行在 `$DSH_HOME/code-toolkit/<session-hash>.json` 写一条记录（先写 running，完成后写 finished + 渲染好的报告）。所以：

- 重开会话后 `/code-status` 仍能读到最后一次结果
- 进程在运行中退出，记录停在 running，`/code-status` 会明确说"上次没跑完"

## 评测

`npm test` 跑确定性检查（提示词树、解析器、渲染器、范围拼装、包元数据），不需要模型。

模型质量用 `evals/ACCEPTANCE.md` 的流程：`evals/cases/` 里的用例物化成临时 git 仓库 → agent 审 → `score.mjs` 对照标注算召回/误报/优先级/格式 → 与"同格式、无 persona"的基线对照 → 改一处、重跑。

## 限制

- 需要宿主提供独立上下文的原生 `spawn` provider；缺失时命令直接报错，不会退化成主 agent 自查。
- `/code-simplify` 默认直接改；加 `report` 只出计划。子 agent 改完必须验证，验证不通过会回退并如实报告。
- 子 agent 被禁止调用委派类工具（`subagent`、`workflow`、专家召唤等），不会二次扇出。
- 报告里的"完成"表示 agent 已返回，不保证它取到了全部 diff 或跑通了测试；具体限制以报告正文为准。
- `/code-caption` 需要宿主支持向会话注入输入（`agent.steer`）；协议以一条用户消息的形式进入会话历史，因此长期会话里它会被压缩，台账文件才是持久的记忆。

## 配置

| 键 | 作用 |
| --- | --- |
| `locale` | 命令文案与回退语言；未设置时跟随宿主 `locale.preference`。报告正文按宿主偏好在 8 种官方语言里选，命令描述只提供中/英，其余语言回退英文 |
| `simplifyModel` | 简化任务使用的模型；不填则跟随当前模型 |
| `reviewModel` | 审查任务使用的模型；不填则跟随当前模型 |
| `reportDirectory` | 报告落盘目录，必须是绝对路径；默认 `$DSH_HOME/code-toolkit` |
| `scrubModel` | 隐私清理任务使用的模型；不填则跟随当前模型 |
| `ledgerDirectory` | caption 台账目录；相对路径按项目根解析，默认 `<项目>/docs/caption` |
| `runTimeoutMinutes` | `sub` 运行超过该分钟数就释放占用，默认 30；`0` 表示不限制。用于「卡在审批上、回合永不结束」的情况 |
| `planMaxAgeMinutes` | `report` 出的方案在这段时间内仍可被下一次执行沿用，默认 60；`0` 表示不限制 |
