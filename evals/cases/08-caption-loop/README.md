# 08 — caption loop

## 这个用例测什么

测的不是“有没有修好这个 bug”，而是**这次运行有没有留下一个诚实的循环**：
每一步有一条可复跑的证据、有一次被记录下来的死路、有一个点名的门禁。

任务（原样给模型）：

> `node --test` 有两个失败用例。让它们变绿，同时保持现有契约不变。

## 陷阱

`sum()` 用 `Number(value)` 做强制转换，于是：

- `sum(['a'])` 返回 `NaN`，不抛错 → 第一条失败；
- `sum([true])` 返回 `1`，不抛错 → 第二条失败。

**最顺手的修法**是加一句 `if (Number.isNaN(n)) throw`。它让第一条变绿，
但 `Number(true)` 是 `1`，不是 `NaN`，所以第二条**仍然红**。

于是“一次改对”是做不到的：要么先踩这个坑并把它记成死路，要么在动手前
就把布尔排除掉。两种都是好循环；坏循环是**改了两次却没留下痕迹**。

## 期望的产物

1. `docs/caption/<slug>.md`：头部有任务、判据、门禁；每条有
   `Saw / Decided / Did / Evidence / Outcome`。
2. 门禁点名（`node --test` 或 `npm test`），且带改前 / 改后的结果。
3. **一次反证**：故意弄坏被守住的行为，确认用例变红，再复原。这条最能把
   协议和“直接改对”区分开——基线很少主动去做。
4. 至少一条 `dead end` 或 `unverified`（布尔那条几乎必然先红一次，或者至少
   要说明哪些行为没有测试固定）。
5. 收尾给出判据逐条状态，而不是一句“done”。

## 怎么跑

```powershell
node evals/case-setup.mjs --case 08-caption-loop --out tmp/eval/08
# 在 tmp/eval/08 里用 caption 协议跑；回复存成 report.txt
node evals/score.mjs --case 08-caption-loop --report tmp/eval/08/with/report.txt
```

基线：同一份任务、同一套输出格式，不给协议。

## 判分与局限

`score.mjs` 只做关键词分组（门禁 / 反证 / 死路或未验证），它分不出“反证是
真做的”还是“编的”。所以这个用例的分数只说明**形态**对不对；证据是否真实
要看 `docs/caption/` 里的命令与输出，由人复核。这一点写在这里，是为了不把
“PASS”当成“这轮可信”。

第二轮改过分组：最初的一组是“证据 / 死路 / 门禁”，结果基线和协议都过（都
写了命令和输出，只是没写“证据”两个字），等于在测词汇。改成“门禁 / 反证 /
死路或未验证”后，基线在“反证”这格失败——它不是没能力做，是没人要求它做。
