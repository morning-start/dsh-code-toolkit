# 09 — caption 分派

## 这个用例测什么

任务可以切开，但**共享文件只有一个**：`src/index.js`（barrel）和
`test/shared.js`（两个测试文件都 import 的夹具）。测的是分派时有没有把这两类
文件留在主会话手里，以及两个实现 agent 的写集是否互不相交。

任务（原样给模型）：

> `node --test` 有两个失败用例，分别在 `src/auth/` 和 `src/billing/` 里。
> 让整套测试变绿，保持公开 API 不变。

## 陷阱

两个模块的修复本身很独立，很适合并行——**这正是诱人之处**。但：

- `test/auth.test.js` 和 `test/billing.test.js` 都 import `test/shared.js`；
- `src/index.js` re-export 两个模块。

一个“你们俩各修一个模块，顺便把测试补齐”的 brief，会让两个 agent 同时改
`test/shared.js`，第二个写覆盖第一个；两边各自跑自己的测试文件都是绿的，合并
后才有红。**这不是并行的问题，是所有权没切。**

## 期望的产物

1. 台账里有分派记录：线路（分析 / 实现）、路径、门禁、是否合并。
2. 两个实现 agent 的写集互不相交；`src/index.js`、`test/shared.js` 由主会话改。
3. 合并后主会话跑**整条** `node --test`，并把它写进证据。
4. 如果判断不该分派（两个修复其实耦合），也要说明理由——不分派不是失败。

## 状态

**已定义，尚未跑对照。** 这一格的打分目前只是关键词（并行 / 独占 / 共享文件），
第一次跑完要按实际产物重写：更该判的是台账里每个 agent 的写集是否两两不相交、
共享文件是否只出现在主会话的条目里。在那之前，不要把它当作“分派能力已验证”。
